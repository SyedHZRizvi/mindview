4.1 — The Software Development Process
Understand-design-code-test-document-maintain; iterative refinement; why coding is only part of the job
# The same five-stage cycle is followed even on a small program. # 1. UNDERSTAND THE PROBLEM # "Compute the average of three test scores" # # 2. DESIGN (IPO + pseudocode) # Input : three numbers from the user # Process: average = (a + b + c) / 3 # Output: print rounded to 1 decimal # # 3. CODE a = float(input("a: ")) b = float(input("b: ")) c = float(input("c: ")) avg = (a + b + c) / 3 print(f"Average: {avg:.1f}") # # 4. TEST — try (90, 80, 70) → 80.0; try (0, 0, 0) → 0.0 # 5. DOCUMENT — header comment, docstrings, README
📖 Lesson Notes — Ontario Curriculum

Writing software is not the same as typing code. It is a process with several distinct stages: understand the problem, design a solution, code it, test it, and document it. After release, you may also maintain the code — fixing bugs and adapting it to new needs. Skipping stages is tempting (especially "design") but expensive: a bug caught in design takes minutes to fix; the same bug caught after deployment can take days. Experienced developers spend more time thinking and reading than typing.

The first stage — understanding the problem — is the most important. You cannot solve a problem you have not stated clearly. A useful technique is to write a one-sentence description of the program's purpose ("This program counts the words in a file"), then list its inputs, its outputs, and any constraints or assumptions ("input is a plain text file; assume ASCII only; the file fits in memory"). If you cannot write these down, you do not understand the problem yet.

The next stage, design, produces a plan before any code. Two common tools are IPO charts (next topic) and pseudocode (the topic after). For larger programs the design also identifies the functions that will need to exist and the data structures they will share. A good design lets you anticipate problems before you have committed code that will be costly to change.

  • Software development process / SDLC — the stages from problem to deployed software.
  • Requirement — a statement of what the software must do.
  • Design — planning the solution before coding.
  • Implementation / coding — writing the code.
  • Testing — verifying the code behaves as required.
  • Documentation — written explanations for future users and maintainers.
  • Maintenance — fixing and updating software after initial release.
  • Iteration — cycling back to an earlier stage when a problem is found.

Worked example — mapping the five stages to a small project

# Task: "Build a quiz that asks 5 multiple-choice questions and reports the score."
#
# 1. UNDERSTAND
#    Inputs: user's choice (a/b/c/d) for each of 5 questions.
#    Output: number correct + percentage.
#    Constraint: questions hard-coded in the program for now.
#
# 2. DESIGN (pseudocode)
#    set score = 0
#    for each question in list:
#        show question and choices
#        read user choice
#        if choice matches the correct answer:
#            score += 1
#    print score and percent
#
# 3. CODE — implement the loop and the question list.
# 4. TEST — try answering all correctly; all incorrectly; mixed.
# 5. DOCUMENT — header comment + a brief README.

Note how design captures the algorithm in plain language. The code stage becomes mechanical: each pseudocode line corresponds to one or two Python lines. Tests are designed once the algorithm is known.

  • Jumping straight to code without writing down what the program is supposed to do — you will end up rewriting.
  • Treating testing as something to skip if the code "looks right" — bugs hide in plain sight.
  • Designing a single monolithic block of code instead of decomposing into functions — hard to debug.
  • Believing documentation is optional — you will be the future reader who is grateful for it.
  • Ignoring requirements ("I'll figure it out as I go") — leads to features that don't match user needs.

Curriculum expectation: Strand B, Expectation B1.1 — "describe the stages of the software-development process (understanding the problem, planning the solution, coding, testing, documenting, maintaining)".

4.2 — IPO Charts and Pseudocode
Input-Process-Output charts; writing pseudocode; flowcharts; translating pseudocode into Python
📖 Lesson Notes — Ontario Curriculum

An IPO chart (Input-Process-Output) is a simple, three-column planning tool used before coding. The Input column lists every value the program receives (from the user, a file, a sensor, etc.). The Output column lists what the program produces (printed text, written files, on-screen graphics). The Process column lists the transformations — the calculations and decisions — that turn the inputs into the outputs. Filling out an IPO chart forces you to think about the program holistically before committing to a particular implementation.

Pseudocode describes an algorithm in mostly-English with a few programming-like conventions. It uses control words like IF, WHILE, FOR, SET, and PRINT, but is not constrained by the syntax of any one language. Indentation indicates structure. The point of pseudocode is to plan the logic without getting distracted by syntax issues. Once the pseudocode is correct, translating to Python (or Java) becomes a mechanical step.

A flowchart is a graphical alternative to pseudocode using rectangles (for processes), diamonds (for decisions), and arrows (for flow). The shape conventions come from a 1960s standard (ANSI X3.5). Flowcharts are excellent for visual learners and for explaining algorithms to non-programmers, but they can become unwieldy for larger programs — that is where pseudocode shines.

  • IPO chart — Input-Process-Output planning tool.
  • Pseudocode — an informal mix of English and programming-like control words.
  • Flowchart — a graphical algorithm diagram (rectangles, diamonds, arrows).
  • Stepwise refinement — starting with a high-level outline and adding detail level by level.
  • Decomposition — breaking a problem into smaller subproblems.
  • Trace — manually following pseudocode on paper with sample inputs.

Worked example — IPO chart for a marks summary

Problem: read a list of student marks and report count, average, and high.

INPUT             | PROCESS                                  | OUTPUT
------------------+------------------------------------------+----------------
- list of marks   | 1. count = length of marks               | "n students"
  (e.g., 5 floats)| 2. average = sum / count                 | "average: X"
                  | 3. highest = maximum of marks            | "highest: Y"
                  | (handle empty list: skip with "no data") |

The IPO chart captures the program's intent in a compact table. Notice how the Process column already mentions the empty-list edge case — design is the right time to think about it, not after the program crashes.

Worked example — pseudocode for the same task

READ marks as a list of numbers

IF marks is empty:
    PRINT "no data"
ELSE:
    SET n = length of marks
    SET total = 0
    FOR each mark in marks:
        ADD mark to total
    SET average = total / n
    SET highest = maximum of marks
    PRINT n, average, highest

Each pseudocode line maps almost directly to a Python statement. SET becomes =, FOR each becomes for ... in, ADD x TO y becomes y += x, and PRINT becomes print. The pseudocode is clear without committing to a language.

  • Writing pseudocode that is so detailed it is essentially Python — defeats the purpose of language independence.
  • Writing pseudocode that is so vague it does not constrain the implementation — "compute the answer" is not a step.
  • Omitting edge cases from the IPO chart (empty input, very large input, negative values) — deal with them in the design.
  • Drawing flowcharts that contain ten levels of nested diamonds — switch to pseudocode at that point.
  • Not updating the pseudocode after the code changes — the two drift apart and only one is correct.

Curriculum expectation: Strand B, Expectation B2.1 — "use IPO (Input-Process-Output) charts and structured pseudocode to plan a solution before coding".

4.3 — Debugging: Finding and Fixing Errors
Syntax vs. runtime vs. logic errors; reading tracebacks; print-debugging; the rubber-duck method; the debugger
# Three kinds of error in three lines: # 1. SYNTAX ERROR — Python won't even start running the program # if x > 5 # missing colon — SyntaxError # print(x) # 2. RUNTIME ERROR — crashes during execution lst = [1, 2, 3] # print(lst[5]) # IndexError: list index out of range # 3. LOGIC ERROR — runs but produces the wrong answer def average_wrong(nums): return sum(nums) / 3 # BUG: should be / len(nums)
📖 Lesson Notes — Ontario Curriculum

Every programmer writes bugs. The job is not to avoid them — that is impossible — but to find and fix them efficiently. Bugs fall into three categories. A syntax error is a violation of the language grammar (missing colon, mismatched quote, wrong indentation). The interpreter refuses to run the program at all and points (usually fairly accurately) at the offending line. These are the easiest to fix once you read the error message. A runtime error happens during execution: the program starts, runs partway, and then raises an exception (ZeroDivisionError, IndexError, ValueError, TypeError). The Python traceback tells you which line raised the exception and through what chain of calls. A logic error is the most insidious: the program runs to completion but produces wrong answers, because the algorithm itself is incorrect. There is no error message; you find these only by testing.

The most reliable debugging tool is print-debugging: sprinkle temporary print(...) statements to display the value of key variables at strategic points. Compare what you see against what you expect; the first place they differ is usually near the bug. Once the bug is fixed, remove the prints (or convert them to proper logging).

The famous rubber-duck method is to explain the code out loud, line by line, to a rubber duck (or any inanimate object). The act of forcing yourself to verbalise often reveals what you had been glossing over. The interactive debugger — pdb in Python, or the visual debugger in Thonny / VS Code / IDLE — lets you set breakpoints, step through one line at a time, and inspect variables without modifying the program. For non-trivial bugs the debugger is far faster than scattering print statements.

  • Bug — a defect in a program.
  • Syntax error — code that violates the language's grammar.
  • Runtime error — an exception raised during execution.
  • Logic error — the program runs but produces wrong output.
  • Exception — Python's mechanism for signalling runtime errors.
  • Traceback — the chain of function calls printed when an exception is raised.
  • Breakpoint — a marker that tells the debugger to pause execution at a specific line.
  • Print-debugging — inserting temporary print statements to inspect program state.

Worked example — reading a traceback

def average(nums):
    return sum(nums) / len(nums)

print(average([]))

# Traceback (most recent call last):
#   File "demo.py", line 4, in <module>
#     print(average([]))
#   File "demo.py", line 2, in average
#     return sum(nums) / len(nums)
# ZeroDivisionError: division by zero

Read tracebacks from the bottom up: the last line names the error (ZeroDivisionError), the line above it shows the exact statement that triggered it, and the lines above that show how we got there (the function call chain). The fix here is to guard against an empty list: if not nums: return 0.

Worked example — print-debugging a wrong answer

def count_evens(nums):
    count = 0
    for n in nums:
        if n % 2 == 1:           # BUG: this counts ODD numbers
            count += 1
    return count

# Add print to see what's happening
def count_evens_debug(nums):
    count = 0
    for n in nums:
        is_even = (n % 2 == 1)
        print(f"  n={n}, is_even?={is_even}")   # diagnostic
        if is_even:
            count += 1
    return count

print(count_evens_debug([2, 3, 4]))
# n=2, is_even?=False    ← wait, 2 IS even
# n=3, is_even?=True
# n=4, is_even?=False
# 1

The trace shows that n=2 is reported as not even — pointing directly at the broken condition. The fix: n % 2 == 0 (an even number leaves remainder 0 when divided by 2). Once verified, remove the diagnostic prints.

  • Reading only the last line of a traceback — the line above usually points at your code, the most useful clue.
  • Trying random changes ("change-and-pray") without understanding what is broken.
  • Forgetting to remove print-debugging statements before committing — clutters real output.
  • Treating a fixed test as proof the bug is gone — write a regression test (a test for the specific bug) so it cannot reappear silently.
  • Ignoring the warning signs of a syntax error (red underline in the editor) and running the program anyway.

Curriculum expectation: Strand B, Expectation B3.3 — "distinguish syntax errors, runtime errors, and logic errors, and explain how each is diagnosed and fixed".

4.4 — Testing and Documentation
Designing test cases (normal, boundary, invalid); test plans; header comments; docstrings; README files
# Quick "manual unit tests" using assert def max_of(a, b, c): """Return the largest of three numbers.""" return max(a, max(b, c)) assert max_of(1, 2, 3) == 3 # normal assert max_of(5, 5, 5) == 5 # ties assert max_of(-3, -2, -5) == -2 # negatives assert max_of(0, 0, 1) == 1 # boundary with 0 print("All tests passed.")
📖 Lesson Notes — Ontario Curriculum

Testing is the discipline of verifying that a program does what it is supposed to do. Manual testing — running the program with sample inputs and checking the output — works for tiny programs but quickly becomes impossible to repeat for anything larger. Professional teams write automated tests: small programs whose only job is to exercise the main program and report success or failure. Even in Grade 11, getting in the habit of testing every function on a handful of inputs is a small effort that catches a surprising number of bugs.

A good test plan covers three categories of input. Normal cases are typical, expected inputs (a function that averages marks should work for [80, 90, 85]). Boundary cases are at the edges of what is legal (empty list, single element, the largest or smallest legal value). Invalid cases are inputs that should be rejected (negative ages, malformed strings). Bugs love boundaries: most off-by-one and special-case errors live there.

Documentation is for future readers, including your future self. The minimum for a small program is a header comment at the top of each file (purpose, author, date) and a docstring for each function describing what it does, its parameters, and its return value. A larger project also includes a README file with installation and usage instructions, and ideally a few sentences describing the overall design. Good documentation does not duplicate the code — it explains why the code does what it does and how to use it without reading every line.

  • Test case — one specific input plus the expected output.
  • Test plan — the collection of test cases covering a function.
  • Normal / typical input — expected, ordinary data.
  • Boundary case — an input at the edge of the valid range (empty, single, max).
  • Invalid input — an input the function should reject.
  • Assertion — a check that a condition is true (Python's assert).
  • Regression — a previously fixed bug that re-appears.
  • README — a plain-text description of a project at its root.

Worked example — designing test cases

# Function under test:
def percent(score, total):
    """Return score as a percentage of total, rounded to 1 decimal."""
    return round(score / total * 100, 1)

# Test plan
# normal:        percent(80, 100)  == 80.0
# normal:        percent(45, 50)   == 90.0
# boundary:      percent(0, 50)    == 0.0
# boundary:      percent(50, 50)   == 100.0
# boundary:      percent(33, 33)   == 100.0     ← exact division
# rounding:      percent(2, 3)     == 66.7      ← documented behaviour
# invalid:       percent(80, 0)    → ZeroDivisionError (or handled)

assert percent(80, 100) == 80.0
assert percent(45, 50)  == 90.0
assert percent(0, 50)   == 0.0
assert percent(50, 50)  == 100.0
assert percent(2, 3)    == 66.7

Eight tests, written once, will run every time we change the function. The invalid case (total = 0) is documented but not asserted here — instead we would either add a guard inside the function or document that callers must not pass 0.

Worked example — a documented function

# grader.py
# Author: A. Lovelace    Date: 2026-05-31
# Purpose: convert percentage marks to Ontario achievement levels.

def to_level(percent):
    """Return the Ontario achievement level for a percentage mark.

    Parameters:
        percent (float): mark between 0 and 100 inclusive.

    Returns:
        str: one of "Level 4", "Level 3", "Level 2", "Level 1", "R".
    """
    if percent >= 80: return "Level 4"
    if percent >= 70: return "Level 3"
    if percent >= 60: return "Level 2"
    if percent >= 50: return "Level 1"
    return "R"

The header comment identifies the file's purpose; the docstring explains the function precisely. A future reader (or you in three months) can understand to_level without reading any of its code.

  • Testing only the easy cases — bugs live at the boundaries.
  • Writing tests that pass even when the code is wrong (e.g., asserting result is not None instead of asserting a specific value).
  • Skipping documentation because "the code is obvious" — it is not obvious to anyone but you, and not even to you in a month.
  • Letting tests rot: if you change the function, update the tests in the same commit.
  • Writing one giant test that does everything — small, focused tests give better failure messages.

Curriculum expectation: Strand B, Expectation B3.1 — "construct a test plan with normal, boundary, and invalid cases; record expected vs. actual behaviour".

4.5 — Sequential File I/O
Why files matter; the with open() as f idiom; reading line by line; writing text; basic CSV reading
# Write a marks file, then read it back and average it. # WRITE with open("marks.txt", "w") as f: f.write("82\n") f.write("76\n") f.write("91\n") # READ total, count = 0, 0 with open("marks.txt") as f: for line in f: total += int(line.strip()) count += 1 print(f"Average of {count} marks: {total/count:.1f}")
📖 Lesson Notes — Ontario Curriculum

Programs that lose their data when they stop running are seldom useful. File I/O is the simplest form of persistence: storing data on disk so it can be re-read on a later run. Python provides a built-in open(path, mode) function that returns a file object. The mode is "r" for read (the default), "w" for write (creates a new file, replaces any existing content), "a" for append (adds to an existing file), and a few others. Once you have a file object you can read or write through it.

The modern, recommended way to use a file is the with statement: with open("data.txt") as f:. The with block is a context manager that guarantees the file is closed when the block ends, even if an exception is raised inside. Forgetting to close a file can leak operating-system handles, lose buffered writes, and on Windows prevent other programs from accessing the file. The bare open without close is a code-smell.

To read a file line by line, iterate over the file object: for line in f:. Each line includes its trailing newline, which is why we usually call .strip(). To write, use f.write(text); this does not add a newline automatically — include "\n" in the text yourself. For tabular data, the standard format is CSV (comma-separated values): one row per line, fields separated by commas. Python's csv module handles edge cases (quoted fields, escaped commas) properly — for messy data, prefer it over hand-rolled .split(',').

  • File — a named, persistent region of storage on disk.
  • Open / close — obtaining and releasing a file handle.
  • Mode — "r" (read), "w" (write/truncate), "a" (append).
  • Context manager (with) — automatically closes the file at block exit.
  • Line — a string of characters ending at a newline.
  • End-of-file (EOF) — the position after the last byte.
  • CSV — comma-separated values; the most common simple tabular format.
  • Path — the filesystem name of a file (relative or absolute).

Worked example — a small log-file writer

def log(message, path="events.log"):
    """Append a timestamped message to the log file."""
    import datetime
    stamp = datetime.datetime.now().isoformat(timespec="seconds")
    with open(path, "a") as f:
        f.write(f"{stamp}  {message}\n")

log("Program started")
log("User logged in: ada")
log("Program ended")

Each call appends a line to the file. Mode "a" means new lines are added at the end — existing content is preserved. The with ensures the file is closed promptly. If the file does not exist, Python creates it.

Worked example — reading a CSV of names and ages

def read_roster(path):
    """Read 'name,age' lines from a CSV; return a list of (name, age) tuples."""
    roster = []
    with open(path) as f:
        next(f)                       # skip header line
        for line in f:
            name, age_str = line.strip().split(",")
            roster.append((name, int(age_str)))
    return roster

# Sample roster.csv:
# name,age
# Ada,17
# Bob,16
# Cay,17

people = read_roster("roster.csv")
for name, age in people:
    print(f"{name} is {age}.")

The function iterates line by line with O(1) extra memory regardless of file size — perfect for very large data. next(f) reads (and discards) the header. The split(",") here is fine because the file is simple; for files with quoted fields containing commas, use import csv and csv.DictReader.

  • Opening a file in "w" mode "just to check" — it truncates the file to empty.
  • Forgetting with and not calling .close() — leaks handles, and writes may not flush to disk.
  • Iterating over a file object twice without seeking back to the start — the second loop sees nothing.
  • Forgetting to convert text read from the file to numbers — line is always a string.
  • Hand-parsing complex CSV with split(',') — quoted commas will break it.
